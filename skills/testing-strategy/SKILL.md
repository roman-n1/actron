# Проверяемое поведение

Адаптировано из testing-strategy KMP Messenger. Перед изменением правила свяжи:
контракт → правдоподобная поломка → допустимый вход/порядок → точный assertion.
Новый баг/поведение: сначала RED по причине контракта. Чистый рефакторинг: исходный GREEN,
перенос, GREEN; добавляй regression test на существенную выделяемую границу.

Используй kotlin.test, runTest и существующие fake/DSL; наблюдай Store через production API,
StateFlow, события, StoreProbe и exceptionHandler. Не открывай private методы ради теста.
Не вычисляй ожидаемый результат тем же алгоритмом, что production.

Для корутин управляй причиной через CompletableDeferred/Channel, runCurrent/advanceUntilIdle;
реальный sleep и подсчёт yield не доказывают завершение. Проверяй cancelled launch, поздний
ответ после выхода из состояния, повтор startup после ошибки и неизменность порядка trace.
Различай cancellation coroutine и CancellationException активного обработчика.

Основная команда — `./gradlew :actron-core:jvmTest`; общую логику проверяй также на JS/Wasm
и iOS по доступности. API/ABI — `:actron-core:apiCheck`. Выбирай потребителей по зависимостям.
Runner мутационного тестирования пока не подключён. Различающие assertions полезны уже сейчас;
не называй мысленную проверку мутационным прогоном и не обещай M без инструмента.

Для конечной фоновой работы можно использовать тестовый awaitIdleForTest: он проверяет нулевые
pending inputs/launches. Для бесконечного launch используй сигналы старта/отмены, затем отменяющее
действие; не ожидай idle до отмены. В многопоточных тестах жди завершения producers до чтения
обычных mutable данных. Yield внутри проверяемого hook может намеренно провоцировать overlap;
фиксированное число yield как ожидание результата недопустимо. Retention-assertions продолжают
проверять реальные структуры; знание приватного layout находится в JVM-only StoreRuntimeInspection.
